    田中です。結論から言うと、T1・T2とも今回の範囲で実現できます。技術は Node.js の標準ライブラリだけで組み、npm 依存は0にします。気になる点は5つあります。 1. **保存**: 9人×31日なので、データは数十KBです。DBは入れず、JSON ファイルに「一時ファイルへ書いてから rename」で保存します。途中で失敗しても旧データが残るので、「保存失敗なら受付済みにならない」を満たせます。再起動後も消えません。スタッフが100人を超えたら SQLite に替えます。 2. **認証**: 「他のスタッフの希望は見えない」を本気で守るなら、ログインが必要です。今回は作りません。スタッフ用APIは「自分の分だけ返す」仕様にします。オーナー用の一覧と計算APIは、環境変数で渡す合言葉(ヘッダ)を必須にします。それでいいか、美咲さんに確認したいです。名前を選ぶだけなので、他人の名前を選べば見えてしまいます。9人の店なら許容範囲だと思いますが、リスクとして明記してください。 3. **週の計算(T2)**: 月曜始まりの週は月をまたぎます。1日が水曜なら、その週の月・火は前月分です。月のシフト案だけを渡すと、前月末の時間が漏れて超過を見逃します。そこで、計算APIは「前月末の週に入っていた分」も任意で受け取れるようにします。渡されなければ、その分は0として扱い、画面に「月初の週は前月分を含まない」と一文出します。 4. **時刻**: 開始・終了は「同じ日の HH:MM」に限ります。日またぎ(終了が開始より前)は入力エラーにします。カフェの営業時間なら足ります。休憩の控除も今回はしません。時給×実働時間で計算し、端数は分単位で計算して、合計の最後に1回だけ円に丸めます。 5. **計算の置き場所**: 人件費と週上限の計算はサーバー側の関数1つにして、POST /api/calc で返します。画面で同じ計算を持つと、ずれたときに原因が追えなくなります。入力のたびに呼んでも、9人×31日なら数ミリ秒です。 分け方は変えません。ただし鈴木さんと、先にAPIの形(リクエスト・レスポンスのJSON)を決めたいです。私が README に書きます。例は、陳さんの「22時間+6時間で週28時間超過」と「時給1,100円×5時間=5,500円」をそのままテストにします。テストは実装より先に書きます。 見積もりは、T1が半日、T2が半日です。根拠は、エンドポイントが約6本、純関数が2つ、テストが約25ケースという見立てです。鈴木さんは、画面に必要な項目で足りないものがあれば言ってください。
